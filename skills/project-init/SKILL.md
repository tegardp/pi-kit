# Project Init

Generate `brainstorm` and `plan` skills for this repo by interviewing the user, then
filling templates. The generated skills are the deliverable — you are not brainstorming
their feature here.

## The one hard rule

Write nothing to disk until the user approves a filled slot table you presented in the
conversation. A generator built on unexamined assumptions produces skills built on them,
and the error compounds twice before anyone notices.

## Step 1 — Read the ground

- The repo: `ls`, README, `git log --oneline -20`, whichever config file names the stack.
- Existing skills: `ls .pi/skills/ ~/.pi/agent/skills/`. If a brainstorm skill exists
  anywhere, read it — it already encodes spec path and commit format, and one in this repo
  is something you are about to replace.
- Existing specs and plans: `ls docs/specs/ docs/plans/`. Real ones beat any abstract answer.

Questions you could have answered by reading are wasted questions. An argument to
`/skill:project-init` is the domain; skip the first question.

Once the interview establishes the stack, the key config file, the test/verify command, and
the commit convention, write them to `.pi/skills/_recon.md` (see the template at the
bottom of this step) after Step 4. The generated `brainstorm`, `plan`, and `execute-plan` skills
check this file before repeating recon that doesn't change between runs — it's a cache for
facts about the repo, not for anything that changes commit to commit.

```
# Recon cache — generated by /skill:project-init on YYYY-MM-DD

Stale if `<key config file>` changes — re-derive rather than trust this file if it has.

- Stack: <e.g. "Node/TypeScript, pnpm, Next.js 14">
- Key config file: `<path>`
- Test/verify command: `<command>`
- Commit convention: `<e.g. type(scope): description, from git log>`
```

## Step 2 — Grill

**One question per message**, never batched — the third usually depends on the first.
**Always attach your recommended answer** in a sentence, so the user can say "yes" nine
times and still get something considered. Recommending is not answering: stop and wait.
**Explore instead of asking** whenever a file can answer it. **Ask branching questions
first** — domain, plan-skill yes/no, reversibility — before detail questions.

Target the slots in `references/slots.md`. Read it now. Don't recite it as a script: if an
answer makes three later questions irrelevant, drop them; if an answer surprises you, chase
it. Chased surprises are what separate a fitted skill from a generic one.

Say the question count up front. Eight to twelve for brainstorm alone, four or five more
with the plan skill. Ask about the plan skill within the first three questions — it reuses
most of this interview, so generating it separately means asking the same things twice and
getting answers that drift.

## Step 3 — Present the slot table

Show every slot with its value. Before presenting, cut two kinds of filler:

**Speculative** — a tier boundary or question axis serving a hypothetical case. Propose
dropping it.

**Generic** — anything true of every software domain ("consider error handling"). The
template already covers the generic case. Slots hold what bites people *here*. If you
can't make one domain-specific, use the template default rather than inventing filler.

## Step 4 — Write

Substitute every `{{SLOT}}` and write:

```
.pi/skills/brainstorm/    SKILL.md, templates/spec.md, evals/pressure-tests.md
.pi/skills/plan/          SKILL.md, templates/plan.md, evals/pressure-tests.md
.pi/skills/_recon.md      stack, key config file, verify command, commit convention
```

`evals/pressure-tests.md` comes from `templates/pressure-tests.md.template`. `_recon.md`
uses the template shown in Step 1 — overwrite it every run, since a re-run of `/skill:project-init`
means the recon it holds should be current.

**Target the repo, not the home directory.** The generated skills are named plainly, so
one set exists per scope. Writing them to `~/.pi/agent/skills/` means the next domain
silently overwrites this one. In `.pi/skills/` each repo carries the version tuned to
its own stack, version-controlled with the code it describes, and reaching everyone who
clones it.

**Check before writing.** If `.pi/skills/brainstorm/` already exists, stop and show the
user its `description` line, tier criteria, its `evals/pressure-tests.md` **Last run** line,
and its frontmatter's `generated-from` version against this kit's current version in
`~/.pi/agent/git/github.com/tegardp/pi-kit/package.json`'s `version` field. A version behind means the templates have since changed and
this skill hasn't — worth mentioning even if you end up keeping it. If `Last run` shows real
runs and rationalization rows earned from them, weigh that against replacing it — those rows
came from actual failures no fresh interview reproduces, and outrank a version bump. If it
still says never and is also behind, that's the case for replacing rather than keeping. Ask
whether to replace it, or whether this domain is close enough that extending the existing
one is better. Never overwrite silently.

If the user is not in a repo, say so and ask where to write. Do not default to home.

- Substitute the value, not a description of it.
- Preserve template prose that isn't a slot. The imperative voice and the reason attached
  to each rule both do work at runtime.
- List slots: three to five items. Longer gets skimmed.
- Where reversibility was "git revert is the whole story", substitute empty for
  `{{RISK_SECTION}}`, `{{RISK_FIELDS}}`, `{{FEATURE_ROLLBACK}}` and clean up the
  whitespace. An empty heading reads as an omission rather than a decision.

The two skills couple in one direction through one artifact: a spec path. Neither imports
the other, and the plan skill must work on a hand-written spec.

## Step 5 — Self-review

- `grep -ro '{{[A-Z_]*}}' <target>/` returns nothing.
- **Descriptions are triggers only.** No workflow summary — a description that names the
  steps becomes a shortcut the agent takes instead of reading the body. This is the single
  most common way a generated skill silently fails.
- **Gate 2 honesty** (plan skill) — does the named prediction mechanism exist in this
  domain? A borrowed gate gets skipped, and a skipped gate is worse than a simpler one.
- **Contradiction** — do tier criteria agree with question axes?
- **Rationalizations are real** — each row should be something an agent would actually say
  under pressure, not a strawman.

Fix inline. Don't loop.

## Step 6 — Hand off and stop

`evals/pressure-tests.md` ships with **Last run: never**. Say so plainly, not just that it
exists: these skills enforce discipline, and discipline holds until someone leans on it.
Ask directly whether the user wants to run the three prompts now, in a fresh session, before
trusting the skill on anything real — don't just mention the file and move on. If they'd
rather do it later, that's fine, but the ask should happen here, not be left implicit.

Report paths, stop. Don't offer to use the new skills on a real feature — a cold session is
the point.

## Failure modes in yourself

**Generating during the interview.** Narrating template text mid-interview means spending
the rest of it defending a draft instead of testing your understanding.

**Domain cosplay.** Shallow familiarity produces confident-sounding slots. A wrong tier
boundary is invisible until it has misrouted three specs. Ask more instead.

**Silent overwrite.** Plain names mean the second run in a repo lands on the first. Check
first, always, and treat an existing skill's rationalization table as the expensive part —
it holds excuses observed in real failures, which no interview reproduces.

**Weak descriptions.** A skill named `brainstorm` is disambiguated only by its description.
If yours would match a design conversation in any repo, it is too vague — load it with
symptoms specific to this stack.
